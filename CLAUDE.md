# flock

A `flock` CLI for agents and a web app for humans, sharing one SQLite database. `README.md` explains the model; `VISION.md` is the long-range direction and yields to the README where they differ; `docs/adr/` records the decisions.

## Setup and daily commands

- `bun test` — the whole test suite. `bun run typecheck` — every package. `bun run build` — `vite build` then `scripts/gen-assets.ts`, producing the web app `flock serve`/a compiled binary embeds. `scripts/setup.sh` is the contributor setup on a fresh clone (`bun install`) and is idempotent; see README's Contributing section. It installs no daemon and never puts a dev build on `PATH`; by default it symlinks `~/.claude/skills/flock` at this checkout (moving aside a prod-installed real file/directory to `flock.bak` first); `--no-skill` skips that.
- `flock up | down | restart | status | logs | url` — the daemon. `start`/`stop` alias `up`/`down`. From an installed binary this spawns one `serve` child; from a checkout (detected by `isStandalone()` being false) it starts the dev environment instead — `bun --watch … serve` plus `bun x vite --strictPort` — on this checkout's ports. Agents may run this. See `docs/adr/0003-per-checkout-dev-environment.md` for the port and worktree scheme and `docs/adr/0012-single-binary-distribution-and-a-daemon-instead-of-pm2.md` for the daemon and distribution design. A failed start stops every child it spawned, and `up`/`restart`/`down` reap this checkout's strays — its own `serve`/vite children, reparented to pid 1, that no live runfile owns (a vite left behind when its API died) — while `status` only lists them; see `docs/adr/0020-reap-orphaned-dev-children.md` (`findStrays` in `packages/cli/src/procs.ts`). `--tailscale`/`--no-tailscale` on `up`/`restart`/`serve` fronts the browser-facing port with `tailscale serve` for an HTTPS origin on the tailnet (`https://<machine>.<tailnet>.ts.net`); precedence `--tailscale`/`--no-tailscale` > `FLOCK_TAILSCALE` > `tailscale` in `~/.flock/config.json` > off (`resolveTailscale` in `packages/cli/src/tailscale.ts`), preserved across a bare `up`/`restart` the same way `--host` is. It refuses — one line, nothing started or left running — rather than warning when tailscale is missing, logged out, HTTPS certs aren't enabled on the tailnet, or `:443` is already mounted elsewhere; `flock down` tears the mount down (`serve … off`, never `reset`). `flock url`/`flock status`/the `up` and `serve` banners list the https URL first once a mount is active, but `--open` still opens the loopback/bound address. See `docs/adr/0019-tailscale-serve-for-an-https-origin.md`.
- `bun run flock <verb>` runs the CLI from source. `scripts/setup.sh --link` opts into a global one: it writes a POSIX `sh` launcher at the install slot (`$FLOCK_INSTALL_DIR`, else `$FLOCK_HOME/bin`, else `~/.flock/bin`) whose body is `exec bun "<checkout>/packages/cli/src/main.ts" "$@"` — no `cd`, so the board still resolves from the caller's directory — setting an installed binary aside as `flock.bin.bak`. Line 2 carries `# flock-dev-launcher: <checkout>`; `scripts/install.sh` and auto-update both detect it and refuse to overwrite (installer: one stderr line, exit 0, `FLOCK_FORCE=1` overrides; `isDevLauncher` in `packages/cli/src/update.ts`). `--unlink` removes the launcher and restores the backup. Dev always wins over prod, with no PATH ordering involved.
- `flock serve [--port N] [--host H] [--open]` runs the web UI plus the HTTP API in the foreground; `--host` defaults to `0.0.0.0` (every interface), precedence `--host` > `FLOCK_HOST` > `host` in `~/.flock/config.json` > `0.0.0.0` (`resolveHost` in `packages/cli/src/dev.ts`; `--host 127.0.0.1` for loopback only). `up` is what backgrounds it; `up --foreground` is the same thing spelled through the daemon verbs. A bare `up`/`restart` with none of `--host`/`FLOCK_HOST` given preserves the host an already-running daemon recorded in its runfile rather than recomputing the default (`preserveRunningHost` in `daemon.ts`), so a daemon started `--host 127.0.0.1` does not silently flip back to wildcard. `flock url`/`flock status` print only what's actually reachable for the bound host, and `flock serve`'s own banner/`--open` use the same first URL (`baseUrl`, never the literal `0.0.0.0`) — see `docs/adr/0015-bind-to-all-interfaces-by-default-and-advertise-only-reachable-urls.md`.
- `flock setup [--no-start] [--skill-only]` writes `~/.claude/skills/flock/SKILL.md` from the binary's embedded copy (a real file, not a symlink; a symlinked destination is left alone) then runs `up`. `flock upgrade [--version=V]` reinstalls deliberately, re-running the embedded installer beside the current binary, refreshing the skill, and restarting a running daemon; an installed flock also does this on its own at most once a day. `FLOCK_NO_UPDATE=1`, or `{"autoupdate": false}` in `~/.flock/config.json` (`docs/config.md`), turns that off; auto-update never runs from a checkout.
- `flock say`/`flock comment` take `--level review|info`, and `flock notify settings`/`flock notify set` read and write who hears what (ADR 0024). Every post carries a notification level: `flock ask` is intrinsically `needs-me` and cannot be declared — `--level needs-me` is refused, exit 1, pointing at `ask`; an image attachment on a card comment and a GitHub PR URL in a body are `review` without a flag; everything else is `info`. The human's four switches (needs-me and review on, everything else and quiet check-in off, 20-minute threshold) live in the `notify_settings` table per actor with an optional per-board override, not in `config.json`. A card comment delivers at `review` and at nothing else, so "everything else" still means the channel (d15, `deliversFor` in `packages/core/src/notify-levels.ts`). `docs/notifications-contract.md` §5 is the shapes.
- Env vars beyond what `flock help` covers (`FLOCK_ACTOR`, `FLOCK_ACTOR_KIND`, `FLOCK_HARNESS`, `FLOCK_MODEL`, `FLOCK_EFFORT`, `FLOCK_DB`): `FLOCK_PORT` sets the API port for `up`/`serve`, `FLOCK_WEB_PORT` the dev web port, `FLOCK_HOST` the bind host for `up`/`serve` (default `0.0.0.0`; `--host` wins over it, and it in turn wins over config's `host`), `FLOCK_HOME` relocates everything flock keeps outside the database (`~/.flock` by default: `run/`, `logs/`, `update.json`, `skill.json`, `config.json`), `FLOCK_TAILSCALE` toggles the `--tailscale` mount the same way (`0`/`false`/`no`/empty are off; below the flag, above config's `tailscale` key), `FLOCK_TAILSCALE_BIN` overrides where the `tailscale` binary is found (else `PATH`, else known install paths — see `docs/adr/0019-tailscale-serve-for-an-https-origin.md`), `FLOCK_SESSION` sets the harness run key a write's events carry (below `--session`, above detection from `CLAUDE_CODE_SESSION_ID`), `FLOCK_NO_UPDATE`, `FLOCK_NO_SETUP` and `FLOCK_FORCE` are the installer/auto-update opt-outs (`FLOCK_INSTALL_DIR` picks the install slot for both `scripts/install.sh` and `scripts/setup.sh --link`).
- `flock telemetry [BOARD] [N] [--refresh] [--json]` prints what the harness sessions behind a card (or behind `--as`/`FLOCK_ACTOR`, with no N) cost, how full their context got, how long they ran, how many tools they swung and whether they are still alive; `--refresh` re-reads every session, even ones already final. Flock never installs or relies on Claude Code hooks: every reading comes from reading a transcript on demand, and since a harness's cost line lands only after the session itself ends, a session with no cost yet is kept a refresh candidate until it has cost, its transcript is gone, or it has simply been too long (bounded, see `isSessionFinal` in `packages/core/src/telemetry-types.ts`). See `docs/harness-telemetry.md` and ADR 0026.
- `close` and `events` are aliases for `done` and `log`; `flock help` does not list them.

## Worktrees

Each checkout serves its own dev environment. The canonical checkout owns :4747 and :5173. A worktree gets its own stable ports (`flock status` lists every running checkout's runfile, from any directory); `flock up` picks them and prints them. Runfiles are namespaced by mode — `flock` for an installed binary's daemon, `dev` for the canonical checkout, `dev@<dir>` for a worktree — so an install and a checkout coexist, and `up` refuses (exit 1) rather than stopping a daemon that is not its own. Never serve the canonical ports from a worktree; `flock up` refuses, and there is no override. See `docs/adr/0003-per-checkout-dev-environment.md` for how the ports are derived.

If :4747/:5173 are already held by something else — typically an installed `flock`'s own daemon — `flock up` in the canonical checkout does not refuse: it falls back to the same offset ports a worktree would get (`portOffset` on the checkout's path) and prints the URL plus a one-line note explaining the fallback. An explicit `--port`/`--web-port`/`FLOCK_PORT`/`FLOCK_WEB_PORT` still wins and still refuses if that port is held; `flock restart` still retakes its own ports rather than falling back. `flock status` also names which binary answered (`process.execPath`, and whether it's this checkout's source build) so the installed-vs-source ambiguity is visible.

The global `flock` binary, if installed, is unrelated to any checkout; dev builds are never on `PATH`. Inside a worktree run the CLI from source: `bun run flock up`. That uses the worktree's code and the worktree's ports.

Worktrees share `~/.flock/flock.db` by default, so the worktree's app shows the same boards as the canonical one. A worktree never migrates that shared file: only the canonical checkout or an installed binary stamps it. When a branch bumps `SCHEMA_VERSION`, the first CLI call or `up` in that worktree seeds a private `.flock/flock.db` copy (with a `seeded-from-shared` marker) and uses it from then on, printing one line saying so; an older worktree opening a newer shared file proceeds with a stderr warning instead of exiting. `flock status` says how to rejoin once the shared file has caught up. See `docs/adr/0021-a-worktree-never-stamps-the-shared-database.md` (`packages/cli/src/schema-policy.ts`). Use `bun run flock up --isolated` when you want throwaway data regardless; that creates the same private `.flock/flock.db`, which the CLI also picks up automatically from inside the worktree. `up` is idempotent: re-running it reports "already running", starts fresh, or restarts only the processes whose settings (like `--isolated`) changed.

## Scratch data

Seed data for eyeballing a UI change never goes on the shared DB. Either run `bun run flock up --isolated`, or point `FLOCK_DB` at a file in your scratchpad for both the CLI and `flock up` (`up` passes it through to the API and web processes). `flock board new --project /tmp/...` does not change the database: `--project` only sets the board's scoping directory, and with `FLOCK_DB` unset the write still lands on `~/.flock/flock.db`. A board that reaches the shared DB anyway is deleted before the work is reported done: `flock board delete <slug> --yes`.

## Layout

- `packages/core` — the `Flock` class over bun:sqlite. Every domain rule lives here: claim CAS, frontier, awaiting-human, events, project scoping, body task checkboxes, image attachments, notification levels and the settled tracker (`notify-levels.ts`, `settled.ts`, ADR 0024), markdown export and import, the `schema_version` guard on open (with the ADR 0021 `migrate`/`allowNewer` policy). No dependencies.
- `packages/cli` — arg parsing, human and `--json` output, `flock serve`. `daemon.ts` is the pidfile-based supervisor behind `up|down|restart|status|logs|url` (binary mode spawns one `serve` child; checkout mode reuses `dev.ts`'s pure port/worktree helpers). `setup.ts` writes the skill and starts the daemon. `telemetry.ts` is `flock telemetry [BOARD] [N] [--refresh] [--json]` plus the best-effort read `done`/`release` do — no hook-facing path; flock never installs or relies on Claude Code hooks (d10). `update.ts` is auto-update (stamp, lock, CalVer compare, re-running the embedded installer) plus `flock upgrade`/`self-update`; `paths.ts` holds `flockHome()` and `personalizationPath()` so `update.ts` doesn't drag `dev.ts` into every CLI invocation's startup. `runtime.ts` is `isStandalone()`/`version()`/`embeddedAssets()` — what lets one binary tell a checkout from a compiled executable and carry the built web app, `scripts/install.sh`, and `skills/flock/SKILL.md` inside itself.
- `packages/harness` — one `HarnessReader` per harness behind a registry, and nothing else. `claude-code.ts` resolves a run key to a transcript by the `(cwd, session id)` encoding, scans it bounded (size, line count, timeout — `limits.ts`), and computes liveness from the pid file plus the transcript's mtime, with a UTC-vs-local `procStart` guard against pid reuse. Types only from core; it never touches the database, and core never touches the filesystem. Tests run off `fixtures/claude-code/`, never the real `~/.claude`. See `docs/adr/0026-harness-telemetry.md` and `docs/harness-telemetry.md`.
- `packages/server` — Hono routes mirroring `Flock` methods; SSE by tailing the events table; serves the embedded assets map (preferred) or `packages/web/dist` (checkout fallback), plus `GET /install.sh`. `telemetry.ts` refreshes a card's or actor's non-ended sessions on read (15s TTL, single-flight per run key, bounded concurrency, an ended session never re-read) and strips the stored transcript path off loopback. `POST /api/presence` and the push pump's batching/presence suppression (ADR 0021) live in `push.ts` and `index.ts` beside the rest of push, as do ADR 0024's `GET`/`PUT /api/notify/settings` and the `x-flock-notify: review|info` header on the message and comment routes; `presence-log.ts` holds the pure log formatters and the loopback gate behind the `[presence]`/`[push] decision` lines and the loopback-only `GET /api/presence` dump (card 54 observability, documented in `docs/notifications-contract.md` §2.3). Only one process delivers push for a given database at a time: every pump tick claims a lease row in that database first, and a follower stays quiet and fast-forwards (`acquirePushLease` in core, `claimLead` in `push.ts`, ADR 0023) — several `serve` processes on the shared `~/.flock/flock.db` is the normal state of a dev machine, and without the lease each one sent its own copy of every notification.
- `packages/web` — Vite and React. Hash routes are `#/b/<slug>`, `#/b/<slug>/c/<n>`, `#/b/<slug>/a/<actor>`, and `#/b/<slug>/<tab>` (tab is one of cards, channel, activity, decisions). Board views refetch the snapshot on SSE events, but coalesced: a 150ms-debounced, 600ms-ceiling, single-flight refetch, filtered by event type (`useCoalescedRefetch` in `packages/web/src/live.ts`).
- Colour is a token layer: `packages/web/src/styles.css` defines every colour, and every other stylesheet (`brand.css`, `compose.css`, …) consumes tokens and never defines a hex. `bun test` runs a 4.5:1 contrast gate over the stylesheet (`scripts/contrast.ts`, `scripts/contrast.test.ts`); `bun run scripts/contrast.ts` prints the table. See `docs/adr/0011-design-tokens-and-lab.md`.
- `skills/flock` — the user-invoked `/flock [goal]` conductor skill: board as state, subagents work cards, a persistent Monitor over `flock log --follow --json` feeds human writes back into the session. Invoked bare it stands the board and listener up and creates no cards, so the human starts the work from the web UI's channel. `flock setup` writes it as a real file to `~/.claude/skills/flock`, refreshed on upgrade; `scripts/setup.sh` symlinks it at a checkout instead for live-editing (default; `--no-skill` skips it), and `flock setup` detects and preserves that symlink. Agent onboarding text lives in `flock handoff` (`packages/cli/src/handoff.ts`), not in the skill. A user can personalize the skill without losing edits to auto-update: the conductor reads `~/.flock/skill.md` at run start if present (never written or read by flock code itself), which supplements the vendored skill and wins on conflict; see `docs/config.md` and ADR 0014.
- `docs/agents/issue-tracker.md` — the tracker doc for Matt Pocock's engineering skills. Copy it into a project that wants flock as its issue tracker.
- `docs/install.md` — the curl one-liner, what it installs, supported platforms, env overrides, auto-update, and uninstall. `docs/harness-telemetry.md` — what the Run block shows, how a session is linked to a card with no install, the refresh/finality rule for retroactive cost, and the privacy rules (same machine, numbers only, transcript path omitted off loopback). `docs/config.md` — `~/.flock/config.json` (`autoupdate`, and `host` — the bind-host fallback below `FLOCK_HOST` and above the `0.0.0.0` default, ADR 0015).
- `scripts/gen-assets.ts` — walks `packages/web/dist` after `vite build` and writes the gitignored `packages/cli/src/assets.generated.ts` (a committed `.d.ts` is what the rest of the CLI type-checks against). `scripts/build-release.ts` — builds and tarballs one compiled binary per target. `scripts/install.sh` — the POSIX-sh installer, embedded in the binary and also served at `GET /install.sh`.
- `.github/workflows/release.yml` — six-target release matrix, CalVer tag on push to `main`, `SHA256SUMS`. `.github/workflows/install-test.yml` — hermetic installer test on every push, an Alpine/Debian/wget container matrix on release.

## Conventions

- Domain rules go in core with a test. The CLI and server stay thin. Core's tests live in `packages/core/test/`; everywhere else they sit beside the source as `*.test.ts`.
- Attribution is explicit: core methods take an `Actor`, the CLI reads `--as` and `FLOCK_ACTOR`, the server reads `x-flock-actor` and `x-flock-actor-kind` headers. An `Actor` also optionally carries `harness`/`model`/`effort` (see ADR 0005); the server mirrors them as `x-flock-harness`/`x-flock-model`/`x-flock-effort`. It also optionally carries `session` — the harness run key, `<family>:<session id>[#<agent id>]`, auto-detected in Claude Code, `--session`/`FLOCK_SESSION` on the CLI, `x-flock-session` on the server — and that column on `events` is the whole of what links a card to a harness session (ADR 0026). A post's notification level is `--level` on the CLI and `x-flock-notify` on the server, validated identically (`assertDeclarableLevel`).
- One board per project directory, resolved from the working directory. The board argument is optional in most CLI verbs; a few (`boards`, `actors`, `needs-me`, `log --all`) take no board at all, and `board new` / `board import` take `--project` rather than resolving it.
- Address cards by number, and by board slug only when the board is not implied. Never expose internal ids.
- Keep CLI output stable. Agents parse `--json`; humans read the rest. Conflicts (including claiming a blocked, held, or closed card) exit 3, not-found exits 2; `claim --force` claims past a blocker but never past a hold. Everything else exits 1.
- The global database `~/.flock/flock.db` is the default. Tests use `:memory:`.
- Record decisions as a new file in `docs/adr/`, numbered one past the highest existing file, following the format of 0001 and 0002.
